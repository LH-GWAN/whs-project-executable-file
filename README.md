# IDAS

블랙박스 영상(AVI/MP4)에서 GPS·속도·G센서 메타데이터를 추출해 지도와 그래프로
시각화하고, 사건 리포트(PDF)를 생성하는 데스크톱 포렌식 도구. Windows exe로 배포한다.

> 이름이 **GPS Tracer → IDAS**로 바뀌었다. 창 제목, exe(`IDAS.exe`, `dist\IDAS\`), 바로가기
> (`IDAS.lnk`), 사용자 데이터 폴더(`%LOCALAPPDATA%\IDAS`), 레지스트리(`HKCU\Software\IDAS`)가
> 모두 새 이름을 쓴다. 이름은 `core/appinfo.py` 한 곳에서 정한다. 예전 이름의 데이터 폴더
> (`%LOCALAPPDATA%\GPSTracer`)가 있고 새 폴더가 없으면 첫 실행 때 이름만 바꿔 넘기므로 사건
> 이력·증거 폴더는 그대로 유지된다. 안내 창의 "다시 표시하지 않음" 표시(레지스트리)는 옮기지
> 않아 한 번 더 뜬다. 예전 `dist\GPSTracer\`와 `GPSTracer.lnk`는 `clean_windows.bat`이 지우지
> 않으니 직접 지운다.

분석 엔진은 별도 저장소([LH-GWAN/whs-project](https://github.com/LH-GWAN/whs-project))에서
개발된 것을 `engine/vendor/`에 그대로 가져와 쓴다. **이 저장소의 코드는 그 엔진을
호출하고 결과를 시각화하는 레이어**다.

## 독립 실행 (엔진 저장소 불필요)

이 폴더 하나만 있으면 동작한다. 옆에 있는 `../whs-project/`(엔진 원본 저장소)는
**실행에 필요 없다** — 엔진 스크립트 3개가 `engine/vendor/`에 복사돼 있고, 앱 코드
어디에도 그 폴더를 참조하는 경로가 없다.

검증(엔진 저장소가 없는 곳으로 앱만 복사해 확인):
- 소스 실행: 실샘플 추출 정상 (600지점 / fix 60 / `tfdt_trun`)
- exe 실행: **소스 트리를 전부 지운 뒤** `IDAS` + `_internal/`만으로
  MP4 fragmented 600지점, AVI FineVu 1035좌표 추출 + GUI 기동 정상

`../whs-project/`가 필요한 경우는 **엔진을 고칠 때뿐**이다(주의사항 2번 참고).
그때도 원본에서 고친 뒤 `engine/vendor/`로 복사하면 실행 폴더는 계속 독립적이다.

## 모듈별 역할

### `app.py` — 진입점

`--run-engine` 플래그를 **QApplication을 만들기 전에** 확인하고 `engine_entry`로 위임한다.
패키징된 exe에는 별도 `python.exe`가 없어서, 엔진을 서브프로세스로 돌릴 때 앱이 자기
자신을 재호출하기 때문이다. 이 순서가 바뀌면 자식 프로세스가 GUI를 하나 더 띄운다.

### `core/paths.py` — 경로 해석

PyInstaller는 번들 리소스를 `sys._MEIPASS`에 풀어놓으므로 `__file__` 기준 경로가 전부
깨진다. frozen 여부에 따른 분기를 이 파일 하나로 모아, 나머지 모듈은 신경 쓰지 않게 한다.

### `core/format_sniffer.py` — 사전 확인

엔진을 돌리기 전에 "이 파일을 처리할 수 있는가"를 즉시 알려준다. **판별 로직을 다시
구현하지 않고 엔진의 `detect_container()`를 그대로 호출**한다 — 앱은 "지원함"이라 했는데
엔진은 건너뛰는 불일치를 원천 차단하기 위함. 세부 경로(AVI 내 스트림 종류, MP4 내
fragmented/sampletable/udta-mamt)는 엔진이 알아서 고르므로 앱은 관여하지 않는다.

### `engine/registry.py` — 엔진 진입점 정의

엔진이 `integration_blackbox.py` 하나로 통합돼 있어 항목이 하나뿐이다. 엔진이 또 바뀌면
**이 파일만 수정**하면 되도록 격리해 뒀다.

### `engine/engine_adapter.py` — 오케스트레이션

엔진을 서브프로세스로 실행하고, 결과 CSV를 `TrackPoint` 리스트로 표준화한다.
앱의 모든 화면과 리포트가 이 데이터 모델 하나만 본다.

`TrackPoint`의 세 가지 상태 구분이 이 도구의 핵심 개념이다:

| 상태 | 판별 | 의미 |
|---|---|---|
| `has_fix` | 좌표 있음 | GPS 수신 정상 |
| `is_dropout` | GPS 시각은 있는데 좌표 없음 | **수신 끊김** (NMEA status=V) |
| (둘 다 아님) | GPS 정보 자체가 없음 | 이 시점엔 GPS 미기록 (G센서 전용 행) |

### `core/driving_events.py` — 위험운전 행동 판정 (차종별)

예전엔 사건 정보 창에서 급가·감속 임계값(m/s²)을 직접 넣었다. 지금은 **차종(승용차·버스·
화물차)**을 고르고, 국토교통부 보도자료 「급가속 등 위험운전 행동이 교통사고 가능성
높인다」(2022.5.19) 참고2의 **디지털운행기록장치(DTG) 위험운전행동 판별 기준(22년)**을
그대로 적용한다. 기준표는 택시·버스·화물차뿐이라 **승용차는 택시 기준**을 쓴다.

11개 유형 중 속도 변화로 정해지는 넷만 판정한다(방향 계열 - 급진로변경·급앞지르기·급좌우회전·
급U턴 - 은 한때 넣었다가 사용자 결정으로 폐기했다. 과속·장기과속은 도로 제한속도가 영상에 없다).

| 유형 | 승용차(택시) | 버스 | 화물차 |
|---|---|---|---|
| 급가속 (변화 전 6~10 / 10~20 / 20 초과 km/h) | 초당 12 / 10 / 8 km/h | 8 / 7 / 6 | 7 / 6 / 5 |
| 급출발 (5 km/h 이하에서) | 초당 10 | 8 | 6 |
| 급감속 (변화 전 30 이하 / 50 이하 / 50 초과, 감속 후 6 km/h 이상) | 초당 14 / 15 / 15 | 9 / 10 / 12 | 8 |
| 급정지 (감속 후 5 km/h 이하) | 초당 14 | 9 | 8 |

표에 적히지 않은 해석:
- "초당 km/h"는 **1초 창**의 속도 변화다(`core/acceleration.speed_rate_pairs` — 이 측정보다
  1초 이상 앞선 가장 가까운 측정과 비교). 초당 2회 기록하는 기기가 0.5초 차이로 두 배
  부풀려지지 않는다. 같은 종류가 몇 초 이어지면 1건으로 묶는다.
- 속도 구간(6~10, 30 이하 …)은 **변화 전** 속도로 가른다. 급출발은 변화 전 5 이하, 급정지는
  변화 후 5 이하, 급감속은 변화 후 6 이상이다(5~6 km/h로 끝나는 감속은 어느 쪽도 아님).

결과(`DrivingEvent`) 하나를 지도·속도 그래프·Location 표·리포트가 같이 쓴다.
- **지도**: 네 종류를 선 색 + 이름표(마우스를 올리면 시각·판정 근거)로 표시하고, 범례에는
  그 궤적에 나온 종류만 올린다. 겹치면 급정지·급출발·급가속·급감속 순으로 선 색이 이긴다.
- **Speed Analysis**: 그 구간의 **속도 선 색**을 바꿔 보인다(처음엔 구간 전체를 세로 기둥으로 칠했는데 그래프를 가린다는 의견으로 바꿨다). 색 조각은
  전체 곡선의 같은 조각을 덧그린 것이라 모양이 같다.
- **Location Analysis**: `위험운전` 열(속도 옆)에 그 행이 걸친 종류를 모두 적고 행을 그 색으로
  옅게 칠한다. 툴팁에 판정 근거.
- **Location 표의 기본은 1초 단위**(`core/location_table.gps_slot_rows`: GPS 기록이 바뀌는 행만).
  GPS보다 훨씬 자주 행을 쓰는 영상(INAVI 0.1초 G센서 행, VUGERA·FineVu의 반복 기록 -
  `has_frame_detail`)은 탭 오른쪽 위에 **상세보기 (프레임 단위)** 토글이 생기고, 켜면 모든 행이
  나온다. GPS 기록이 없는 행의 위경도는 `-`(예전 "(GPS 없음)"). 분석이 끝나 화면이 열릴 때
  "상세보기가 추가됩니다"(이어보기면 "1, 3번 영상은 …")라고 한 번 알린다. 리포트 표도 1초 단위
  행에서 고르고, CSV는 모든 행을 담는다.
- **리포트**: 차종 기준·기준 요약·위험운전 목록(종류·영상 시각·근거) + 표의 `위험운전` 열.

차종은 `analysis_settings.vehicle_type`에 저장된다. 차종 선택 전의 사건(임계값만 저장)을 다시
열면 승용차 기준으로 다시 판정한다. 이전의 부호 유지 원칙(급감속을 급가속으로 표시하던 버그,
제보: `REC_20240312_082217_F.mp4`)은 초당 속도 변화의 부호로 그대로 지켜진다.

실제 샘플 결과(승용차/버스/화물차): INAVI QXD8000 `REC_20240312_082217_F.mp4` 1/4/9건,
VUGERA `REC_20240916_172436_F.avi` 1/2/2건, 랜드로버 `20250901_215628D.MP4` 1/1/1건,
벤츠 `20240411_144016E.MP4` 0/1(급정지)/2건. FineVu 두 기종은 세 기준 모두 0건.

### `core/outliers.py` — GPS 이상치

터널 출구·고층 건물 사이에서 좌표가 수 km 튀거나 속도가 말이 안 되는 값으로 찍히는 행을
`TrackPoint.is_outlier`로 표시한다. 판정: 좌표 범위 밖/(0,0), 속도 300 km/h 초과·음수,
직전 정상 측정에서 360 km/h 넘는 속도로 150 m 이상 멀어졌다가 다음 측정이 원래 자리 근처로
돌아오는 "튄 점"(마지막 점은 돌아올 점이 없어 튄 것으로 봄). 다음 측정도 튄 자리 근처면
실제 이동(긴 끊김 뒤 재수신)으로 보고 건드리지 않는다. 같은 측정값을 반복 기록한 행은
함께 표시한다. 이상치는 `has_fix`가 False가 되어 지도·그래프·위험운전 판정·주소 조회에서
빠지고, 좌표 표·리포트에는 "(이상치)"로 남으며 원본 값과 사유는 툴팁·CSV에 그대로 있다.
끊김(`is_dropout`)과는 구분한다(좌표가 있으니 끊김이 아니다). 판정은 파이프라인과 재열기
양쪽에서 매번 다시 한다.

### `core/pipeline.py` — 분석 파이프라인

해시 → 형식 확인 → 사건 폴더 생성 → 원본 복사 → 엔진 추출 → duration/위험운전 판정 →
이력 기록. `reopen_case()`는 엔진 재실행 없이 저장된 CSV만 다시 읽는다(빠르고, 원본
영상이 이동식 매체로 사라져도 결과 조회 가능).

### `storage/history_store.py` — 사건 이력

SQLite는 **검색/색인용**이고, 실제 증거(원본 사본·엔진 출력·리포트)는 폴더에 파일로 둔다.
DB가 손상돼도 증거는 살아남고, 다른 포렌식 도구가 이 앱 없이 폴더만으로 접근할 수 있다.

사건번호·담당자·메모는 History 우클릭 > **사건 정보 수정**으로 나중에 고칠 수 있다
(`ui/case_edit_dialog.py`). DB와 `case.json`에 반영되고(`pipeline.update_case_json`,
`info_updated_at` 기록), 사건 폴더 이름과 분석 결과는 그대로 둔다. 예전 DB에 없는 컬럼
(`rear_video_filename`)은 `HistoryStore._migrate()`가 `ALTER TABLE`로 보탠다 — `CREATE TABLE
IF NOT EXISTS`는 기존 표를 바꾸지 않는다.

삭제는 Home의 [선택 삭제]/[전체 삭제](Delete 키, 우클릭 메뉴)로 하며 `core/case_deletion.py`가
맡는다. 확인 창에서 "사건 폴더도 함께 삭제"(기본 켜짐)를 끄면 목록에서만 지운다. 안전장치:
cases 루트 **바로 아래**의 `<사건번호>_<id>` 폴더만 지우므로 DB가 엉뚱한 경로를 가리켜도
다른 곳은 건드리지 않는다. 폴더는 **먼저 `<폴더>.deleting`으로 이름을 바꾼 뒤** 지운다 —
Windows는 안에 열린 파일이 있으면 이름 변경부터 실패하므로 "반쯤 지워진 폴더 + 남은
레코드" 상태가 생기지 않고, 실패하면 레코드를 남겨 다시 시도할 수 있다. 원본에서 복사된
읽기 전용 속성은 풀고 다시 지운다. 그래도 남은 `.deleting` 폴더는 다음 삭제 때 다시
시도한다. 사용자가 다른 곳에 저장한 리포트 PDF는 지우지 않는다. 삭제 전에 영상 재생기의
파일 잠금을 항상 푼다(재생기는 마지막으로 Tracker를 켠 사건의 영상을 계속 잡고 있을 수
있다). 분석이 진행 중일 때는 진행 창이 모달이라 삭제 조작이 막히고, 혹시 요청이 들어와도
거절한다(진행 중인 사건의 레코드를 지우면 워커가 외래키 오류로 죽는다).

```
%LOCALAPPDATA%/IDAS/
├── history.db
└── cases/<사건번호>_<id>/
    ├── source/           원본 영상 사본 (해시로 무결성 고정)
    ├── engine_output/    엔진 산출물 원본 그대로
    ├── case.json         DB 유실 대비 사람이 읽을 수 있는 사본
    └── report.pdf
```

### `ui/map_server.py` — 지도 리소스 서버

배경지도(PMTiles)는 한 파일에서 필요한 타일만 바이트 범위로 읽는 포맷이라 HTTP
Range(206) 의미론이 필요하다. Qt 커스텀 URL 스킴으로는 206을 제대로 돌려줄 수 없어
표준 HTTP를 쓴다. **`127.0.0.1`에만 바인딩**하고 임의 포트를 쓰며, 앱 자신의 정적
파일과 지도 파일만 서빙한다. 사건 GPS 좌표는 이 서버를 타지 않는다.

### 속도 그래프 (`ui/speed_chart_widget.py`)

- **점에 마우스를 올리면 말풍선**: 점에서 12px 안에 마우스가 오면 점을 고리로 강조하고
  영상 시각(mm:ss)·GPS 시각(UTC+9)·속도·가속도(1초 앞 실측 대비, m/s²와 초당 km/h, 부호 유지)·
  좌표·걸친 위험운전(급가속·급출발·급감속·급정지)과 판정 근거를 보여준다. 가속도는 위험운전
  판정과 같은 함수(`core/acceleration.speed_rate_pairs`)에서 나오므로 판정 값과 늘 일치한다.
  화면에 그릴 때만 점 위치를 기록해 두고(`record_positions`) 리포트 이미지에는 말풍선을
  넣지 않는다. 화면 밖으로 나가면 말풍선을 왼쪽/아래로 뒤집는다.

- **점이 실측값, 선은 점을 정확히 지나는 보간선.** 단조 3차 보간(Fritsch-Carlson)이라 곡선이
  모든 측정점을 통과하고 두 점 사이에서 값 범위를 벗어나지 않는다(없는 값을 지어내지 않음).
  이전의 "구간 중점을 지나는 2차 베지에"는 점을 살짝 비켜 가서 검토에서 "점과 선이 왜
  다르냐"는 질문이 나왔다. 선형 연결은 아니다 — 꺾임만 둥글린 것이다.
- 시간 눈금은 10초 주눈금(실선·라벨) + 5초 보조눈금(점선). 영상이 100초를 넘으면 눈금이
  10개 안쪽이 되는 간격을 고른다. 눈금선 알파를 22→85로 올렸다(검토: "선이 안 보인다").
- 화면과 리포트 이미지는 같은 `_paint_to()`로 그린다.

### 리포트의 이동 경로 지도 (기준 그림)

리포트에는 **분석 직후 전체 경로에 맞춰진 지도**가 들어간다. `MapView.set_track()` 뒤 페이지가
`window.__trackDrawn`/`__trackIdle`(MapLibre `idle`, 카카오 `tilesloaded`)로 "다 그렸다"고
알리면 조작 요소(따라가기 버튼·상태 표시·줌 컨트롤)를 잠시 숨기고 한 번 캡처해 둔다
(`baseline_png`). 사용자가 이후 확대·축소해도 리포트는 이 그림을 쓴다 — 검토에서 한반도
전체가 보이게 축소한 채 리포트를 만들자 경로가 점 하나로 나왔다. 탭이 안 보이면(숨은 웹뷰는
빈 그림이 찍힌다) 보일 때까지 기다리고, 타일이 8초 안에 안 와도 일단 찍는다. 기준 그림이 아직
없으면 현재 화면을 대신 쓴다.

### Tracker 재생 조작·전후방·정보 줄

- **배속**(0.5×~2×)과 **±3초** 버튼(5초는 너무 많이 건너뛴다는 의견). 지도 마커는 재생기의
  `positionChanged`를 따라가므로 느리게 틀면 같이 느려진다(별도 처리 없음).
- **재생 막대 클릭**: 막대 아무 곳이나 누르면 그 위치로 바로 간다(`_SeekSlider`). 기본 QSlider는
  누른 쪽으로 한 칸씩만 움직여서 원하는 곳을 눌러도 안 넘어갔다. 누른 채 끌면 그대로 드래그.
- **이름표가 영상 창에 가려짐**(Windows 제보: 전방을 눌러 키우면 "전방"이 안 보임, 후방은 보임 - macOS
  헤드리스에선 재현 안 됨): QVideoWidget 안의 네이티브 영상 창이 커지며 이름표 위로 올라온 것으로 보고,
  이름표(`_VideoPane._caption`)를 네이티브 창(`WA_NativeWindow`)으로 두고 크기가 바뀔 때마다 `raise_()`한다.
- **지도 따라가기 상자는 70%**(가장자리 15%). 80%는 마커가 가장자리에 거의 닿아야 움직였다.
- **파일 창 전에 안내창**: "전방 영상을 선택해 주세요" 같은 문구를 파일 창 제목에만 두면 잘 안 보인다는
  의견으로, 전후방·이어보기에서는 파일 창을 열기 전에 `QMessageBox`로 먼저 알린다(`HomeView._notice`).
- **키보드**: 왼쪽(영상 쪽) 칸 아무 곳이나 누르면(`_KeyPanel`이 초점을 받음) ←/→ 1초, 스페이스
  재생/정지, `,`·`.`(`<`·`>`) 한 프레임(영상의 프레임 빈도, 못 읽으면 30fps). 재생·건너뛰기 버튼,
  막대, 배속, 음량은 초점을 받지 않는다 - 예전엔 방향키가 재생 버튼 → -5초 → +5초 → 막대 순으로
  초점만 옮겨서, 막대에 초점이 갔을 때만 1초씩 움직였다.
- **전방/후방 같이 보기**: Home의 체크박스를 켜면 전방 파일을 고른 뒤 후방 파일을 하나 더
  고른다(`core/video_pairs.py`가 `_F↔_R`, `_N↔_R` 짝을 기본값으로 띄움). 후방은 분석하지 않고
  사건 폴더 `source/`에 사본만 두며(DB `rear_video_filename`, case.json), Tracker에서 영상
  칸을 반으로 나눠 왼쪽 전방·오른쪽 후방으로 재생한다. 후방 재생기는 전방의 재생/정지/위치/
  배속을 따라가고 0.4초 이상 어긋나면 맞춘다. **파일 하나에 비디오 트랙이 둘인 영상**은
  옵션과 무관하게 두 번째 트랙(`setActiveVideoTrack(1)`)을 후방으로 띄운다. 헤드리스에서는
  디코딩을 확인할 수 없어 실제 화면에서 봐야 한다.
- **파일 하나에 두 트랙(랜드로버 순정 블랙박스 등)**: 4번 샘플 `20250901_204119D.MP4`는 1920×1080
  비디오 트랙이 둘이고 프레임을 뽑아 보면 1번이 전방(오버레이 있음), 2번이 후방이다. 후방 재생기의
  트랙 전환(`setActiveVideoTrack(1)`)은 **미디어가 로드된 뒤**(`_on_rear_media_status`)에 해야
  한다 — 로드 전에 부르면 무시돼서 후방 칸도 전방을 틀었다(검토 제보 "둘 다 전방", 오프스크린으로
  재현·검증: 로드 전 지정 → 활성 트랙 0, 로드 후 지정 → 1).
- **2트랙 영상 안내**: 파일을 고르면 `core/video_tracks.count_video_tracks`가 컨테이너를 직접 읽어
  비디오 트랙 수를 센다(MP4 `moov/trak/mdia/hdlr`=vide, AVI `strh`=vids. 재생기는 로드해야 알려
  줘서 쓸 수 없다). 둘 이상이면 "해당 영상은 전방/후방 영상이 붙어 있는 영상입니다. 전방/후방 영상을
  동시에 보여드릴까요?" 안내와 [예, 같이 보기] [전방만 보기] [후방만 보기] [아니요 (취소)]를 띄운다.
  선택(`track_mode` both/front/rear)은 DB(`cases.track_mode`, 마이그레이션)와 case.json에 저장돼
  다시 열 때도 같다. 후방만 보기는 전방 재생기 하나로 2번 트랙을 틀고 이름표 `후방`을 단다. 2트랙
  파일이면 따로 고르는 후방 파일은 받지 않는다(이미 들어 있다). 트랙이 하나인 파일은 안내 없이
  기존 흐름. **보기 표기**: History 항목과 Analysis 파일 정보 줄에 `- F`(전방만) / `- B`(후방만) /
  `- F, B`(같이, 후방을 별도 파일로 붙인 사건도)를 붙인다(`core/video_tracks.view_tag`). 같은 파일을
  전방만으로 분석한 뒤 후방만으로 다시 분석하면 다른 분석이므로 **"이미 분석한 파일" 경고는 보기
  방식까지 같은 이력이 있을 때만** 낸다(`same_view`). 실측: 랜드로버(1920×1080 ×2), 벤츠
  DriveView(전방 3840×2160 + 후방 2560×1440),
  FineVu X3000 AVI(2560×1440 ×2)가 2트랙이고 2번 트랙 프레임을 뽑아 보면 모두 후방이다.
  INAVI·VUGERA·FineVu X700은 1트랙(VUGERA·FineVu X700은 후방이 `_R` 별도 파일).
- **후방 파일 검사(막음)**: 전방/후방 같이 보기로 후방 파일을 고르면 전방과 같은 녹화인지 대조하고,
  하나라도 어긋나면 경고 창을 띄우고 **후방으로 받지 않는다**([다시 고르기] / [전방만 분석], 사용자
  결정). 검사는 두 단계다(`core/video_pairs.py`).
  1. **빠른 검사**(`compare_pair`, 파일 헤더만): 파일 종류(AVI/MP4), 기기 정보(MP4 `ftyp` 브랜드·
     `udta` 박스 구성·udta 안의 모델 문자열, AVI 코덱·ISFT), 영상 길이(2초와 5% 중 큰 값), MP4 mvhd
     녹화 시각(10초), 파일명에 든 시각(3초). 모델 문자열은 랜드로버만 쓴다(`Land Rover Dashcam V1.05
     CH:1`, 채널·버전 숫자를 떼고 비교). INAVI·벤츠는 Ambarella `AMBA` 박스뿐이라 기기로는 못 가른다.
     해상도는 안 본다 — VUGERA 전방 1920×1088·후방 1920×1080처럼 카메라마다 다르다.
  2. **GPS 대조**(`compare_pair_full`, 워커 `ui/pair_check_worker.py` + 진행 창): 두 파일에 엔진을 돌려
     GPS 기록을 뽑고(임시 폴더, 끝나면 삭제) 첫 GPS 시각 차이가 3초를 넘으면 막는다. 같은 UTC 시각의
     좌표를 짝지어 거리 중앙값이 50 m를 넘으면 막는다(3개 이상 짝일 때). **후방(또는 전방)에 GPS
     기록이 없으면 검증할 근거가 없으므로 막는다**("후방으로 선택한 영상에 GPS 기록이 없어 전방과
     대조할 근거가 없습니다", 사용자 결정: 미검증 통과 없음). 대조를 취소하면 전방만 분석.
  왜 GPS까지 보는가: 4번 샘플(랜드로버)의 연속 파일 둘(`…215628D`, `…215728D`)은 길이 60초, mvhd
  녹화 시각, 기기 정보가 전부 같아서 헤더만으로는 못 가른다 — GPS 첫 시각이 60초 다르고 파일명
  시각도 60초 다르다(검토 제보 "다른 영상인데 통과"). 실측: VUGERA `_F/_R` 두 쌍 통과(같은 시각 좌표
  거리 0 m, 대조 1초 안), 랜드로버 연속 파일은 GPS 시각·파일명 시각으로 차단, INAVI vs QXD8000은
  MP4 브랜드(avc1/iso4)·길이·시각으로 차단, GPS 없는 MP4를 후방으로 주면 근거 없음으로 차단.
- **전방/후방 이름표와 클릭 확대**: 두 영상이 있을 때만 각 영상 위에 작게 `전방`/`후방`을
  적는다. 한쪽 영상(또는 이름표)을 누르면 그쪽이 **3:1**로 커지고 다시 누르면 반반으로
  돌아온다(`_VideoPane`, `ENLARGED_RATIO`). 영상 위젯을 겹치는 진짜 PiP는 쓰지 않았다 —
  Qt6 QVideoWidget은 안에 네이티브 영상 창을 두므로 위에 다른 위젯을 올리면 가려진다.
  클릭은 그 영상 창이 입력을 투과시키는(`WindowTransparentForInput`) 덕에 QVideoWidget
  으로 오고, 이벤트 필터로 받는다(오프스크린에서 실측).
- **날짜·시간 줄**: 영상 위에 현재 재생 지점의 GPS 기록 시각을 `2024-03-12 17:22:17 (UTC+9)`
  형식으로 표시한다. NMEA 시각은 UTC라 `core/gpstime.py`가 한국 시간(UTC+9 고정)으로 옮기고
  자정을 넘기면 날짜도 넘긴다. 엔진의 ISO 형식과 원본 `ddmmyy`/`hhmmss.ss` 둘 다 읽는다.
  날짜 없이 시각만 있으면 시각만, 시각이 없으면 마지막 값을 유지한다(좌표가 없는 status=V
  행에도 시각은 대개 있어 좌표와 별개로 갱신).
- **정보 줄은 "재생 시각 이하의 마지막 GPS 기록 행"을 보여 주고, 그 행이 GPS 주기(+흔들림 여유
  0.15초)보다 오래됐으면 `(GPS 미기록)`**이다(`_slot_point`). 즉 기록 하나는 한 주기 동안 유효하고,
  그 주기의 기록이 빠지면 0.15초 뒤부터 미기록이 뜬다. 기기는 GPS보다 훨씬 자주 행을 쓴다(INAVI는 0.1초마다
  G센서 행, GPS는 그중 1행). 예전엔 재생 시각 이하의 마지막 행을 그대로 봐서 GPS 행 사이의 G센서
  행마다 "미기록"이 떴다(검토 제보). 첫 GPS 기록 전과 기록이 끝나고 한 주기가 지난 뒤도 미기록.
  주기는 GPS 기록 값이 바뀌는 시점 간격의 중앙값 근처 평균(`estimate_gps_interval`, 같은 기록이
  초당 31행 반복되는 VUGERA도 1초)이고 0.1초 단위와 3% 안이면 거기에 맞추며 못 구하면 1초.
  **Location 표와 리포트는 그대로 모든 행을 적는다**(G센서 행도 증거라서, 사용자 결정).
  - **GPS 기록 행의 기준은 "시각 필드 또는 좌표"**다. FineVu(자체 72바이트 형식)는 좌표·속도만
    쓰고 NMEA 시각이 없어서, 시각 필드만 보던 첫 구현에서는 표에는 다 나오는데 영상 밑에는
    "미기록"만 떴다(검토 제보). 시각이 없으면 좌표·속도가 바뀌는 시점으로 주기를 잡는다.
  - 처음엔 t0+k·주기 슬롯에 가장 가까운 행을 고르는 방식이었는데 버렸다. FineVu는 좌표와 속도가
    초 안의 다른 시점(약 0.35초·0.75초)에 갱신돼 슬롯 하나에 값 변화가 두 번 들어가고, 주기를
    1.0003으로 잡으면 정수 초마다 경계 직전이 되어 앞 초의 값이 보이는 등 화면 오버레이와
    어긋났다. 재생 시각의 최신 행은 오버레이와 같다.
  - FineVu 속도 파싱 검증: 화면 오버레이(기기가 프레임에 찍는 `047km/h`)와 정보 줄을 대조했다.
    X3000 5/12/20/27초 → 60/47/36/18, X700 10/20/26초 → 40/17/0 모두 일치. Location 표에서 속도가
    "일정해 보이는" 것은 GPS가 1초에 한 번 갱신되는데 기기가 초당 17행을 쓰기 때문이다(같은 값이
    17번 반복). 초 단위로 보면 60→18 km/h로 자연스럽게 줄어든다.
- **정보 줄**: GPS가 없는 순간(미기록·끊김·이상치)에는 속도·좌표를 지우지 않고 마지막 정상값을
  그대로 두며, 오른쪽에 `(GPS 미기록)`/`(GPS 끊김)`/`(이상치)`만 표시한다 — 1초마다 "미기록"
  으로 바뀌면 읽을 수 없다는 검토 의견.
- **정보 줄·시계 줄의 크기는 내용과 무관하게 고정**한다. 처음엔 `(GPS 미기록)`이 나타날 때마다
  줄이 넓어져 영상 칸이 커졌다 작아졌다 했고(검토 제보), 그 바람에 옆 지도 컨테이너 크기가
  바뀌어 카카오 지도의 `resize` 재맞춤이 불려 확대까지 풀렸다. 속도/좌표/상태 칸은 가장 긴
  문구 폭으로 고정하고 주소는 `…`로 줄이며(`_ElideLabel`), 줄 전체는 폭을 레이아웃에 요구하지
  않는다(`QSizePolicy.Ignored`). 검증: 상태 문구가 바뀌거나 긴 주소가 들어와도
  `video_container.minimumSizeHint()`와 영상 분할선 폭이 그대로다.
- **영상 길이**: 재생기가 길이를 0으로 주는 경우(가끔 AVI 첫 로드)에 대비해 파이프라인이
  계산한 길이를 슬라이더·시간 표시의 대비값으로 쓴다(`set_duration_hint`). 조각(moof/mdat) MP4는
  mvhd duration이 0이라 `core/duration._mp4_fragment_duration`이 트랙별 마지막 조각의 tfdt +
  sample duration 합으로 계산한다(INAVI QXD8000 `REC_20240312` 60초, 벤츠 샘플 60초 실측, mdat은
  읽지 않아 0.02초). 엔진 timeline 폴백은 그 다음이다.
- **이전 미디어의 낡은 상태 이벤트 무시**: `QMediaPlayer.setSource()`는 이전 미디어를 멈추면서
  그 미디어의 `mediaStatusChanged`(LoadedMedia 등)를 소스가 바뀌기 전에 동기적으로 내보낸다
  (실측). 그대로 처리하면 첫 장면 띄우기(`_prime_pending`)가 낡은 이벤트에 소모돼 새 파일은 검은
  화면으로 시작하고, 2트랙 파일 다음에 다른 파일을 열면 이전 파일의 트랙 수를 보고 후방 칸을 다시
  켠다. 그래서 `load_video`가 지정한 소스(`_front_url`/`_rear_url`)와 재생기의 현재 소스가 같을
  때만 상태·길이 이벤트를 처리한다.
- **무결성 표시등**: 파일 정보 줄의 해시 옆 작은 점. 사건을 열 때마다 사본을 다시 읽어
  원본 해시와 비교해 초록(일치)/빨강(불일치)/회색(사본 없음)으로 켜진다(HashWorker). 전방·후방
  같이 보기면 해시 칸에 `전방 12자… / 후방 12자…` 둘을 보이고 표시등은 두 사본을 다 대조한다
  (후방 사본도 분석 때 원본과 SHA-256을 대조해 왔지만 화면에는 전방만 나왔다). 클릭하면 둘 다 뜬다.

### 연속 영상 이어보기 (`core/video_sequence.py`)

블랙박스는 10분을 한 파일로 쓰지 않고 1분 파일 10개로 나눠 쓴다. Home의 **연속 영상 이어보기**를
켜고 Upload하면 여러 파일을 한 번에 고르고, 한 사건으로 이어 분석한다.

- **고르기**: 파일 창에서 여러 개 선택 → 녹화 시각순으로 자동 정렬 → 확인 창(순서·시작 시각·길이).
  하나만 고르면 이어보기 없이 그 영상만 분석한다. 전·후방 트랙이 한 파일에 든 영상이 섞이면
  보기 방식을 한 번만 묻고 모두에 적용한다.
- **전·후방 같이**: 두 옵션을 같이 켜면 "전방 영상들을 선택해 주세요" → "후방 영상들을 선택해 주세요"
  순으로 고르고, 후방마다 짝 전방(파일명 짝 규칙 또는 시작 시각 3초 안)을 찾아 전·후방 대조
  (`core/video_pairs` 기준 그대로)를 한다. 짝이 없는 구간은 "n번 영상의 후방(전방) 영상이 없습니다"로
  묻고 [영상 선택]하면 대조 후 넣고, [제외하고 진행]하면 그 구간만 한쪽 영상으로 재생한다(전방 5·후방
  4처럼 수가 달라도 된다). 짝 전방이 분명한데 대조에 실패한 후방은 막는다.
- **검사(엄격, 끊김 없는 것만)**: 파일 크기는 보지 않는다.
  1. 형식·기기: 컨테이너 종류와 기기 서명(모델 문자열·MP4 브랜드·udta 구성·AVI 코덱)이 1번과 같아야 한다.
  2. 시각 근거: 영상 0초의 시각 = GPS 기록 UTC − 그 행의 영상 시각(앞 7개 중앙값). GPS 시각이 없는
     기기(FineVu)는 파일명 시각. 모든 영상이 같은 근거를 가져야 하고, 근거가 없으면 막는다
     ("GPS 기록이 없어 이어지는 영상인지 검증할 근거가 없습니다").
  3. 이어짐: `앞 시작 + 앞 길이`와 `다음 시작`이 ±5초 안. 벗어나면 "N분 뒤에 시작"/"겹칩니다"로 막는다.
  4. 위치: 앞 영상 마지막 좌표 ↔ 다음 영상 첫 좌표 거리가 그 사이 시간 × 두 영상 최고 속도 + 50 m 안.
  실샘플: 랜드로버 `215628D`+`215728D`는 순서를 거꾸로 넣어도 정렬돼 통과, 여기에 `204119D`를 섞으면
  "74분 뒤에 시작"으로, VUGERA EVT+REC는 "90일 뒤", INAVI+랜드로버는 기기 정보 3건으로 막힌다.
- **분석**(`pipeline.run_sequence_pipeline`): 영상마다 원본↔사본 SHA-256 대조(사본 이름 `01_…`,
  `02_…`), 엔진 출력은 `engine_output/seg01…`, 위험운전도 영상마다 판정한다(두 파일 사이 1초 안팎은
  어느 영상에도 없는 시간이라 경계를 넘는 판정은 하지 않는다). 그 뒤 시간축으로 이어 붙인다
  (`combine_segments`: 시각 += 앞 영상 길이 합, `TrackPoint.segment_index`). **이어 붙인 영상 파일은
  만들지 않는다** - 재인코딩하면 원본과 다른 파일이 된다. 구간 목록은 DB `segments_json`과
  case.json `segments`에 남고 다시 열 때 그대로 복원한다.
- **해시**: 파일마다 따로 검증한다(사용자 결정). Composed에서는 해시 칸에 `N개 파일 모두 일치`와 표시등만,
  마우스를 올리면 파일별 해시 목록, 클릭하면 목록 전체가 뜨고 복사된다. 리포트에는 파일별 표.
- **Tracker**: 재생 목록(`load_playlist`). 재생 막대·시각·지도는 이어 붙인 시간축을 쓰고, 재생기는 지금
  영상만 연다. 한 영상이 끝나면(EndOfMedia) 다음 영상을 바로 튼다. 막대로 다른 영상 구간을 누르면
  그 파일을 열고 그 위치로 간다(멈춘 상태면 그 위치 화면을 띄움). 시계 줄 오른쪽에 `영상 2/3 · video2`.
- **지도**: 이어진 궤적. 영상마다 끝나는 곳에 검은 점, 영상이 바뀌는 곳은 선으로 잇지 않는다.
- **Speed / Location**: 탭 위에 `Composed | video1 | video2 …`. Composed 그래프는 영상 경계에 세로 점선과
  이름, 표는 video1 → video2 … 순으로 합치고 맨 앞에 `영상` 칸. 영상별을 고르면 그 영상만(0초부터)
  보이고 파일 정보 줄도 그 영상으로 바뀐다. 리포트 그래프는 늘 Composed로 그린다.

### 지도 현재 위치 화살표

현재 위치는 진행 방향으로 돌린 화살표다. 방향은 GPS 진행각(`track_deg`, 3 km/h 이상 이동
중일 때)을 우선하고, 없으면 다음(없으면 이전) 좌표와의 방위각을 쓰며 정지 중에는 마지막
방향을 유지한다(`ui/map_view.compute_headings`). 방향을 모르면 원으로 그린다. MapLibre는
캔버스로 만든 화살표 이미지 + `icon-rotate`, 카카오는 CustomOverlay 안의 SVG를 CSS
`rotate`로 돌린다.

### Tracker 영상 첫 장면

영상을 올린 직후 검은 화면 대신 첫 장면이 보이도록, 미디어가 로드되면 150ms 재생했다가
멈추고 0초로 되돌린다(재생기는 한 번 재생을 시작해야 프레임을 그린다). 그동안의 재생 상태
변화는 재생 버튼에 반영하지 않는다. **헤드리스에서는 영상 디코딩을 확인할 수 없어 실제
Windows 화면에서 봐야 한다.**

### 리포트 PDF 여백

`report/report_builder.py`의 `ReportExporter`는 `printToPdf`에 A4·좌우 20mm·상하 18mm의
`QPageLayout`을 넘긴다. **CSS `@page` 여백은 QtWebEngine이 인자로 받은 레이아웃에 눌려
반영되지 않았고**, 인자를 안 주면 기본 여백이 0이라 내용이 종이 왼쪽 끝에 붙어 나왔다
(실측: 왼쪽 여백 20.1mm로 확인).

### `ui/map_view.py` — 지도 위젯

Python → JS는 `runJavaScript()` 단방향 주입만 쓴다(지도가 되물어볼 일이 없어 채널 유지
불필요, 준비 경쟁조건도 사라짐). 렌더 프로세스가 죽으면 최대 3회까지 자동 복구하고,
복구 후 보던 궤적을 다시 그린다.

### 지도 사용 방식 — 오프라인 / 온라인(카카오맵)

첫 실행 때 `ui/map_mode_dialog.py`가 오프라인·온라인 중 하나를 고르게 하고, 값은
`%LOCALAPPDATA%/IDAS/settings.json`(`map_mode`)에 남는다. 나중에 화면 우측 상단
**⚙ 설정 > 지도 사용 방식** 메뉴에서 바꿀 수 있다(메뉴바가 아니라 홈 화면 제목 줄의 버튼이다 —
메뉴바는 눈에 안 띈다는 피드백으로 옮겼다). 이 값과 안내 창의 "다시 표시하지 않음"(레지스트리
`HKCU\Software\IDAS`, QSettings)은 **사용자 데이터 영역**이라 `clean_windows.bat`이나
재빌드로는 지워지지 않는다 — 그래서 두 번째 실행부터는 묻지 않는다. 처음처럼 다시 묻게
하려면 **설정 > 지도 설정 초기화** 메뉴를 쓰거나, clean 스크립트 끝의 "Reset app settings"에
Y를 답한다(사건 이력·증거 폴더는 어느 쪽도 건드리지 않는다). 수사 자료를 다루는 도구라 "외부로 나가는가"는
사용자가 알고 고르는 것이지 프로그램이 조용히 정할 일이 아니다.

| | 오프라인 (기본) | 온라인 |
|---|---|---|
| 페이지 | `map.html` (MapLibre + `assets/*.pmtiles`) | `map_kakao.html` (카카오맵 JavaScript SDK) |
| 외부 통신 | 없음 | 지도: 화면 범위가 카카오로 전송. 주소: 좌표가 카카오로 전송 |
| 필요한 것 | 지도 파일 | `assets/online_keys.json` (JavaScript 키 + REST API 키) + 인터넷 |
| 주소 표시 | 안 됨 | Tracker 하단·Location 선택 행에 지번 주소 |

어느 페이지를 띄울지는 `MapServer.map_url()` 하나가 정한다 — 온라인인데 키가 없으면
오프라인 페이지로 간다. 두 페이지는 `renderTrack` / `setPlaybackTime` / `setFollow`
함수 이름이 같아서 `ui/map_view.py`는 어느 쪽인지 모른다.

키가 없는 채로 온라인을 고르면 `ui/online_keys_notice.py`가 발급·도메인 등록·파일 저장
절차를 안내한다(배경지도 안내와 같은 방식, [설정] 메뉴에서 다시 볼 수 있음). 발급 절차
전체는 [`assets/README.md`](assets/README.md)에 있다.

키는 `core/appconfig.online_keys()`가 읽는다. 우선순위는 `settings.json`의
`kakao_js_key` / `kakao_rest_key` > `assets/` 안의 키 파일. 재빌드 없이 키를
바꿀 수 있게 설정 쪽을 위에 뒀다. 키 파일은 이름을 고정하지 않고 폴더 안의 `.json`/`.txt`
후보를 모두 읽어 **영문 소문자·숫자 32자 형식**인 값만 키로 인정한다(예시 문구·BOM·깨진
따옴표 대응). 파일 목록/수정 시각이 바뀌면 2초 안에 다시 읽으므로 재시작이 필요 없고,
안내 창의 [다시 확인]은 즉시 다시 읽어 지도를 온라인으로 바꿔 띄운다. 어떤 파일을 왜 못
썼는지는 `key_status_report()`가 안내 창과 `--diagnose`에 파일별로 적어 준다.
exe는 `_internal/assets/`를 보므로 빌드 뒤에 넣어도 된다(BUILD.md). 세 종류 키 중 **JavaScript 키는 지도, REST API 키는
주소 변환**에 쓰고 네이티브 앱 키는 쓰지 않는다(Android/iOS 전용).

온라인 페이지의 준비/실패는 페이지 안의 `window.__onlineMapState`(`loading` → `ready`
또는 `error:<원인>`)로 알리고, `MapView`가 잠시 폴링해 `online_map_failed` 시그널로
올린다. 원인 종류(`quota`/`domain`/`disabled`/`key`/`network`)는 `core/kakao_api.py`의
`KIND_*`이고, `MainWindow`가 원인별로 한 번씩 안내 창을 띄운다(한도 초과면 "오프라인
지도로 전환" 버튼을 기본으로).

## 데이터 흐름

```
영상 업로드
   ↓
SHA-256 계산(HashWorker) → 같은 해시의 이력이 있으면 "이미 분석한 파일입니다" 확인
   (예: 새 사건으로 다시 분석, 기존 이력은 그대로 / 아니요: 홈으로)
   ↓
core.format_sniffer.sniff()          엔진의 detect_container() 재사용
   ↓
core.pipeline.run_analysis_pipeline()   (ui.workers의 백그라운드 스레드에서 실행)
   ├─ core.hashing                   SHA-256
   ├─ 사건 폴더 생성 + 원본 복사
   ├─ engine.engine_adapter.run_full_extraction()
   │     └─ 서브프로세스: app.exe --run-engine blackbox -o <출력> <입력>
   │           └─ engine_entry → integration_blackbox.main()
   │                 ├─ AVI → integration_avi.py
   │                 └─ MP4 → integration_mp4.py
   │        결과: timeline.csv / coordinates.csv / ... 를 TrackPoint로 변환
   ├─ core.duration                  재생시간
   └─ core.driving_events            위험운전 행동 (차종 기준)
   ↓
ui.analysis_view.load_result()
   ├─ Tracker  : 영상(QMediaPlayer) + 지도, 재생 위치 동기화
   ├─ Speed    : 속도 그래프 + 급가속·급출발·급감속·급정지 강조
   └─ Location : 지도(위험운전 전 종류) + 좌표 테이블(위험운전 열)
   ↓
Report 버튼 → PDF / CSV / 둘 다 선택 → report.report_builder(PDF), core.location_table(CSV)
```

### Report 형식과 일시

Report를 누르면 **PDF / CSV / PDF + CSV**를 고른다. CSV는 Location Analysis 표를 그대로(모든 행, 지도 링크
칸만 뺌, 이어보기면 `영상` 칸 추가) UTF-8(BOM)로 쓴다 - 엑셀에서 한글이 깨지지 않는다. 화면 표와 CSV는
같은 함수(`core/location_table.row_texts`)로 칸 글자를 만든다. PDF 기본 정보에는 **분석(추출) 일시**(사건을
만든 시각)와 **보고서 생성 일시**를 한국 시간(UTC+9)으로 넣고, 전·후방이면 후방 파일·후방 SHA-256을,
이어보기면 영상별 파일·길이·SHA-256 표를 넣는다. 긴 경로·해시는 `overflow-wrap: anywhere`로 종이 폭에서
줄을 바꾼다(예전엔 원자료 CSV 경로가 잘려 나갔다). "AVI 복구" 줄은 AVI 사건에만 넣는다.

## ⚠ 주의할 점

코드를 고치기 전에 반드시 읽을 것. 대부분 실제로 문제가 발생해서 알게 된 것들이다.

### 1. 엔진은 서브프로세스로만 실행할 것

`integration_*.py`의 `main()`과 argparse는 실패 시 `sys.exit()`을 호출한다.
`SystemExit`은 `Exception`이 아니라 **`except Exception`으로 잡히지 않아** GUI 프로세스에서
직접 import해서 부르면 앱 전체가 죽는다. 서브프로세스로 격리하면 이 위험이 사라지고,
사건 이력에 남길 실행 로그(stdout/stderr/종료코드)도 자연스럽게 확보된다.

단, `detect_container()`처럼 `sys.exit()`을 부르지 않는 순수 함수는 직접 import해도 안전하다.

### 2. `engine/vendor/`는 직접 수정하지 말 것

원본 저장소(`../whs-project/`)에서 그대로 가져온 파일이다. 여기만 고치면 원본과
갈라져 다음 갱신 때 충돌한다. **엔진 버그는 원본 저장소에서 고치고 vendor로
복사**해서 두 곳이 항상 바이트 동일하게 유지한다(`diff -q`로 확인). 갱신 절차와 확인 항목은 [`engine/vendor/README_VENDOR.md`](engine/vendor/README_VENDOR.md) 참고.

특히 **엔진 갱신 시 `idas.spec`의 `hiddenimports`를 반드시 다시 확인**해야 한다.
vendor는 데이터 파일로 번들되어 PyInstaller의 정적 분석 대상이 아니라서, 엔진이 새로
쓰기 시작한 표준 라이브러리가 빠지면 **얼린 뒤에야** `ModuleNotFoundError`로 터진다
(실제로 `shlex`에서 겪음).

### 3. 시간축은 엔진이 계산한 `start_time_sec`를 쓸 것

GPS 문장의 UTC로 시간축을 만들면 수신이 튀는 기기에서 축까지 같이 튄다(엔진 README
실측: QXD8000/Mercedes에서 GPS UTC 간격이 0/1/2초로 불규칙한데 구조 기반 축은 완전 균일).
영상 재생과 동기화하는 게 목적이므로 컨테이너 구조에서 계산한 값이 맞다.

경로별 시간축 근거(`time_source`): `tfdt_trun`(fragmented) / `stts`(sample table) /
`gps_utc_elapsed`(udta-mamt) / `avi_video_duration`(AVI).

### 4. 가속도는 "서로 다른 GPS 측정값" 사이에서만 계산할 것

많은 기기가 GPS 갱신 주기보다 훨씬 빠르게 레코드를 쓴다. 그 사이 행들은 **직전 측정값을
그대로 반복한 것**이라 서로 다른 시점으로 취급하면 안 된다.

> **실측 사례**: VUGERA는 초당 31행을 쓰는데 GPS는 1초에 한 번만 갱신된다. 초 경계의
> 속도 변화 3.18 km/h를 행 간격 0.033초로 나누면 **26.8 m/s²** 가 나온다. 실제로는
> 0.88 m/s²인 완만한 가속인데, 38초 영상에서 급가속이 30건 검출됐다.
> FineVu도 연속 행의 94.1%가 완전 중복이었다.

`_distinct_fix_indices()`가 중복을 걷어낸다. UTC가 있으면 UTC로 묶고(정차 중이라 좌표·속도가
같아도 측정은 매초 새로 이뤄지므로 값으로만 묶으면 안 됨), FineVu처럼 UTC가 없는 이진
포맷은 값으로 묶는다.

### 5. "좌표 없음"을 전부 수신 끊김으로 보지 말 것

GPS 1Hz / G센서 10Hz인 기기에서는 좌표 없는 행 대부분이 수신 장애가 아니라 그냥 GPS가
안 실린 샘플이다. 뭉뚱그리면 **정상 주행이 수신 장애로 오독**된다.

> **실측 사례**: INAVI QXD8000은 600행 중 540행이 G센서 전용인데, 이걸 끊김으로 세니
> "GPS 끊김 540개 지점"이라 표시되고 지도의 궤적 전체가 점선(경로 불확실)으로 그려졌다.

판별 기준은 `TrackPoint.is_dropout` — 엔진이 GPS 문장을 파싱했으면 좌표가 비어도
날짜/UTC는 채워주므로 그걸로 구분한다.

### 6. MapLibre `interpolate`는 표현식 최상위에만

줌 기반 `interpolate`를 `match` 안에 중첩하면 MapLibre가 **레이어를 통째로 거부**한다
(콘솔에 `Only one zoom-based "step" or "interpolate" subexpression may be used`).
도로가 통째로 안 그려지는데 예외는 안 나므로 알아채기 어렵다. `interpolate`를 바깥에 두고
각 줌 구간 값 안에서 `match`로 종류별 굵기를 고를 것.

### 7. 지도 초기화는 `load` 이벤트만 믿지 말 것

MapLibre의 `load`는 **렌더 프레임이 최소 한 번 돌아야** 발생한다. GPU 드라이버가
불안정하거나 원격데스크톱/가상머신이면 렌더 루프가 안 돌아 이벤트가 영영 오지 않고
화면이 "지도 준비 중…"에서 멈춘다. `map.html`은 이벤트 + 폴링을 함께 쓰고, 8초 안에
안 되면 사용자에게 사유를 표시한다.

또 Chromium은 **화면에 보이지 않는 페이지의 타이머를 억제**한다. 탭 안의 지도는 그 탭이
열릴 때 `ensure_map_loaded()`로 로드한다(두 탭의 지도를 동시에 띄우면 WebGL 컨텍스트를
두 벌 쓰는 낭비이기도 하다).

### 8. 배경지도 레이어 이름은 Protomaps 스키마

`earth` / `water` / `landuse` / `roads` / `buildings` / `boundaries` 를 쓴다.
OpenMapTiles의 `transportation` / `building` 이 **아니다**.

### 9. macOS 개발 시 venv 위치

`~/Desktop` 하위에 만든 venv는 Qt 플랫폼 플러그인 로드에 실패한다(macOS 폴더 접근
제한으로 추정). 플러그인 파일은 존재하고 직접 dlopen도 되는데 Qt가 못 찾는다.
`~/dev/` 등 Desktop 밖에 만들 것. Windows 배포에는 영향 없는 개발 환경 한정 이슈다.

### 10. 리포트는 전체 좌표를 넣지 않는다

수천~수만 지점이 나오므로 위험운전 구간을 우선 포함하고 나머지는 앞부분 일부만 싣는다
(최대 200행). 원본 전체는 `engine_output/`의 CSV에 그대로 보존돼 있다.


### 11. 엔진 실패는 종료 코드로 알 수 없다

`integration_blackbox.main()`은 하위 스크립트의 예외를 잡아 요약만 찍고 `None`을
반환한다. 모든 파일이 SKIP돼도 프로세스 종료 코드는 0이다. 그래서
`engine_adapter._classify_outcome()`은 종료 코드가 아니라 **산출물**로 판정한다:
좌표가 있으면 정상, 좌표는 없지만 다른 산출물이 있으면 이 영상에 GPS가 없는 것,
산출물이 아예 없으면 엔진 실패. `ExtractionResult.status`로 UI에 노출된다.

### 12. 슬랙 카빙 결과는 본 궤적과 절대 합치지 않는다

`--slack`으로 나오는 `slack_coordinates.csv`는 **과거 녹화분**이라 현재 영상의
재생 시각이 없다(sample table 밖 영역이라 절대 offset만 남는다). 지도·타임라인·
재생 동기화에 쓰면 안 되므로 `ExtractionResult.slack_points`에 따로 담는다.

**슬랙 처리 방향(2026-10)**: 잘라내지 않고 무시한다. 예전 엔진은 AVI에서 옛 녹화 잔재(movi 안
RIFF)를 보면 `_wo_slack.avi`로 잘라내 그걸로 추출했는데("AVI 복구"), 이제 기본은 원본 그대로
추출한다(idx1은 현재 녹화분만 가리키므로 결과는 같다 - 실샘플 VUGERA 2246개 그대로). 잘라내려면
`--avi-opt=--repair-slack`. 슬랙 안의 옛 GPS는 `--slack`으로 MP4·AVI 모두 `<out>/slack/`에
카빙한다(엔진 `integration_avi.run_slack_carve_avi`, NMEA 텍스트만 - FineVu 72바이트 이진은 시그니처가 없어
못 찾고, 사용자 결정으로 하지 않는다). 슬랙 영역은 세 가지다: movi 안의 옛 녹화 잔재(`embedded`), 첫
RIFF가 선언한 크기 뒤에 **옛 녹화 파일이 통째로 이어붙은 경우**(`appended_riff` - 예전엔 뒤의 RIFF를
정상 파일로 세서 놓쳤다), 미상 꼬리(`trailing`). MP4는 free/skip 박스·gap·꼬리에 더해 두 번째 `ftyp`
부터 끝까지(`appended_file`). 실샘플 두 개를 이어붙여 확인: AVI는 뒤 파일 GPS 2271건, MP4는 69건이 나온다.

- **고를 때 묻는다**: 파일을 고르고 해시를 낸 뒤 엔진 `--detect-slack`(추출 없이 `SLACK_JSON` 한 줄,
  `engine_adapter.detect_slack`)으로 슬랙 유무·크기를 보고, 있으면 "슬랙 데이터가 있습니다(n번 영상
  … MB). 따로 뽑을까요?"를 묻는다(사건 정보 창의 'MP4 슬랙 카빙' 체크박스는 없앴다). 미참조 영역
  기준이라 free 박스·꼬리 영역이 있는 대부분의 파일에 뜬다 - 실샘플 13개 중 10개. 실제로 옛 GPS가
  나온 것은 벤츠(5건, 2023년 기록일)와 INAVI QXD8000(9건)이었다.
- **화면**(`core/slack.py`, `ui/slack_tab.py`): 뽑았고 GPS가 있으면 파일 정보 줄 밑에
  `슬랙 데이터 [video1] [video3]` 줄이 생기고, 누르면 `Slack · videoN` 탭으로 간다. 탭에는 **영상 없음**
  (옛 녹화 잔재라 재생할 영상이 없다, 사용자 결정)과 요약, 지도만 있다. Speed/Location에는
  `… 슬랙` 묶음이 붙는다(위험운전 판정 없음). 시간축은 슬랙 첫 기록의 GPS 시각 기준 경과 초
  (`slack_track`), 시각 없는 행은 표에만 뒤에 붙는다. 이어보기·전후방이면 영상마다 따로 묻고 따로
  칸을 만든다(분석 대상인 전방/주 영상만 본다).

### 13. G센서는 개별 축이 아니라 합력으로 본다

엔진의 자가 보정(`*_g_cal`)은 크기만 맞추고 **장착 각도는 보정하지 않는다**.
어느 축이 진행 방향인지 모르므로 개별 축값은 기기 간 비교 기준이 못 된다.
`TrackPoint.g_magnitude`는 방향과 무관한 합력(√(x²+y²+z²))을 쓴다 —
정상 주행이면 중력 때문에 1g 근처로 나온다(실측 0.69~1.41g).

### 14. PyInstaller windowed 빌드에서는 sys.stdout이 None이다

vendor 엔진 세 파일 모두 `sys.stdout.encoding`을 None 검사 없이 읽는다.
`console=False` 빌드에서 GUI 프로세스가 `format_sniffer` → `integration_blackbox`를
import하는 순간 `AttributeError`로 죽고, 콘솔이 없어 트레이스백도 안 보인다.
vendor는 수정하지 않는 원칙이라 `app.py`의 `_ensure_std_streams()`가 import 전에
더미 스트림을 채워 방어한다. **이 함수를 지우면 exe가 안 켜진다.**

### 15. 카카오 JavaScript 키는 페이지 출처(포트 포함)를 등록해야 응답한다

카카오 SDK는 요청의 `Referer` 출처가 카카오 디벨로퍼스 **Web 플랫폼 사이트 도메인**과
정확히 일치해야 응답한다. 실측: `401 domain mismatched! caller=http://127.0.0.1:48213`.
지도 페이지는 로컬 서버에서 열리므로 포트가 매번 바뀌면 등록이 불가능하다. 그래서
`ui/map_server.py`는 **48213 → 48214 → 48215 순으로 고정 포트**를 시도한다(모두 막혀
있으면 임의 포트, 이때 온라인 지도는 "도메인 미등록" 안내가 뜬다).

카카오 디벨로퍼스에서 할 일(계정 소유자만 가능):
1. 내 애플리케이션 > **카카오맵 > 사용 설정 ON** (꺼져 있으면 `403 App disabled
   OPEN_MAP_AND_LOCAL service`로 지도·주소 둘 다 거절된다)
2. **[앱] > [플랫폼 키] > JavaScript 키 > [JavaScript SDK 도메인]**에 `http://127.0.0.1:48213`,
   `http://127.0.0.1:48214`, `http://127.0.0.1:48215` 등록

두 번째 항목에서 실제로 겪은 함정 두 가지:
- **[제품 링크 관리 > 웹 도메인]은 다른 설정이다.** 카카오톡 공유 링크용이라 여기 넣으면
  계속 `domain mismatched`가 난다(카카오 데브톡에 같은 사례 다수).
- **JS SDK 도메인은 JavaScript 키별로 붙는다.** 앱에 JavaScript 키가 여러 개면 도메인이
  등록된 키를 `online_keys.json`에 넣어야 한다. 현재 앱(IDAS, 1572145)은 대표 키가 아닌
  두 번째 키(`9cfb…1967`)에 등록돼 있어 그 키를 쓴다. 대표 키로 바꾸면 지도가 안 뜬다.
  어느 키에 등록됐는지는 콘솔 플랫폼 키 화면에서 "JS SDK 도메인" 배지로 구분된다.

`IDAS.exe --diagnose`가 등록할 주소와 키 유무(마스킹)를 출력한다. 페이지가 SDK
로드에 실패하면 브라우저는 이유를 숨기므로, 로컬 서버의 `/online-map-diagnose`가 같은
조건으로 다시 받아 보고 원인을 돌려준다(성공 경로에서는 부르지 않는다 — SDK 로드
횟수가 한도에 잡힌다).

### 16. API 키 파일은 git에 넣지 말 것

이 저장소는 공개돼 있다. `assets/online_keys.json`은 `.gitignore`에 있고, 빌드하는
PC의 `assets/`에 있을 때만 `idas.spec`이 번들에 넣는다. 배포된 exe 안에는 키가
그대로 들어가므로(데스크톱 앱의 한계) 유출되면 카카오 디벨로퍼스에서 재발급하고,
재빌드 없이 바꾸려면 `settings.json`에 새 키를 넣으면 된다(주의사항 15의 우선순위).

팀에 나눠줄 때는 배경지도와 같은 방식이다 — 키 파일을 외부 공유 링크(구글 드라이브,
뷰어 권한이면 충분)에 올려 두고 `core/appconfig.py`의 `ONLINE_KEYS_DOWNLOAD_URL`에 적으면
안내 창의 [키 파일 내려받기] 버튼이 그 링크와 넣을 폴더를 연다. 링크를 아는 사람만 받을 수
있고 저장소에는 키가 남지 않는다. 키를 소스에 적거나 base64 같은 인코딩으로 감춰 올리는 건
누구나 풀 수 있으므로 하지 말 것.

### 17. 한도 초과(429)는 세션 동안 차단하고 한 번만 안내한다

무료 한도는 앱 단위 일일 집계(지도 SDK 30만 건, 좌표→주소 10만 건, 2026-09 기준).
초과하면 HTTP 429가 온다. `core/geocode.py`는 429나 키 오류를 한 번 보면 세션 동안
`_block`에 담아 더 묻지 않고, `AddressResolver`가 `failed` 시그널을 한 번만 낸다.
지도 사용 방식을 다시 고르면(`reset_block`) 재시도한다.

카카오는 **짧은 시간에 몰린 요청도 429**로 거절하는데 일일 한도 초과와 구분할 수
없다. 그래서 주소 워커는 요청 간격을 0.4초 이상 띄우고 가장 최근 지점 하나만 조회한다.
같은 좌표는 약 11m(소수 4자리) 단위로 캐시해 재생 중 같은 지점을 반복 조회하지 않는다.

### 18. 주소 조회는 GUI 스레드에서 직접 부르지 말 것

`geocode.describe_location()`은 네트워크를 탄다. 화면은 `geocode.cached_address()`로
즉시 확인하고, 없으면 `AddressResolver.request()`에 맡긴 뒤 `resolved` 시그널로 받는다.
재생 중 초당 수십 번 불리는 `_update_info()`에서 동기 호출하면 창이 멈춘다.

### 20. 사건 정보 창에서 Enter는 Start다

QDialog에 기본 버튼을 정하지 않으면 Qt가 먼저 만든 버튼(Cancel)을 autoDefault로 골라,
사건번호만 치고 Enter를 누르면 **취소**됐다(검토 제보). `start_btn.setDefault(True)` +
`cancel_btn.setAutoDefault(False)`로 고정했다. 버튼 순서를 바꿔도 이 설정은 유지할 것.

### 19. 온라인 페이지는 외부 스크립트를 받는다

`ui/vendor/`의 "CDN 금지" 원칙은 오프라인 페이지 얘기다. `map_kakao.html`은 설계상
`dapi.kakao.com`에서 SDK를 받고 타일도 카카오에서 온다. 오프라인 모드에서는 이 페이지가
아예 열리지 않으므로(`map_url()`) 외부 통신 0이라는 보장은 그대로다.

### 온라인 지도(카카오맵) — 2026-09-09

**실제 카카오 지도 위에 궤적이 그려지는 것까지 확인했다.** 카카오맵 사용 설정 ON +
JS SDK 도메인 등록 후, 도봉구 일대 40지점(끊김 2, 급가속 6) 궤적을 앱의 지도 페이지에
넣어 도로·건물·지명 위에 실선/점선/빨간선과 시작·끝·현재위치 마커가 나오는 것을 브라우저로
봤다. 헤드리스 WebEngine에서도 SDK `ready`, 타일 21장, 폴리라인 5개, 주소 변환
(`서울 중구 태평로1가 31`)까지 통과. 단 헤드리스 `grab()`은 빈 이미지라 리포트용 지도
캡처는 실제 화면에서 확인해야 한다(BUILD.md의 기존 주의와 동일).

컨테이너 크기가 작을 때 초기화되면 지도가 구석에 작게 그려지고 범위 맞춤도 그 크기
기준이 되는 것을 실측해서, `resize` 시 `map.relayout()` + 궤적 재맞춤을 넣었다. 재맞춤은
**사용자가 아직 확대/이동을 한 번도 안 했을 때만**(`viewTouched` false) 한다 — 처음엔
따라가기만 켜져 있으면 늘 다시 맞춰서, 옆 패널 글자가 바뀌어 지도 칸이 조금만 커져도
확대가 풀렸다(검토 제보). `zoom_changed`(우리가 맞추는 중이면 제외)·`dragstart`가 손댄
것으로 기록하고, 새 궤적을 그리면 다시 초기 상태다. 오프라인 MapLibre는 크기가 바뀌어도
확대를 그대로 두므로 손댈 것이 없었다(실측: zoom 17 유지).

그 밖에 확인한 것:

- 실제 SDK 호출 실패 경로: 헤드리스 WebEngine에서 `map_kakao.html`을 띄워 SDK 로드 실패
  → 로컬 진단 → `error:domain` 상태 → `MapView.online_map_failed("domain", …)` 시그널까지
  전 구간 동작. 상태 문구 "카카오 디벨로퍼스에 이 프로그램 주소가 등록되지 않음"
- 가짜 SDK를 주입한 렌더링: 좌표 없음/GPS 끊김/급가속이 섞인 12지점 궤적이 실선 2·점선 1·
  빨간선 1로 나뉘고(공유 정점 포함 13개 좌표), 시작/끝/현재위치 오버레이, 화면 맞춤,
  가장자리 도달 시 `panTo`, 따라가기 끄면 이동 없음, 재렌더 시 이전 선 제거
- 지도 서버: 48213 고정 포트, 두 번째 인스턴스는 48214, `/map-config`·`/online-map-diagnose`,
  키 없으면 온라인이어도 오프라인 페이지, 경로 순회 차단 유지
- 실측 응답 분류: 401 도메인 불일치 / 403 사용 설정 꺼짐 / 401 키 없음 / 429 → 한도 초과
- 주소 변환: 캐시(11m), 일시 실패는 차단 안 함, 429·키 오류는 세션 차단 후 호출 0,
  오프라인 모드에서 호출 0. 워커는 연속 요청 중 마지막 것만 조회하고 실패는 한 번만 보고
- 안내 창: 원인별 한 번씩, 한도 초과 창의 "오프라인 지도로 전환" 버튼이 설정을 바꾸고
  지도를 다시 띄움
- 오프라인 페이지(`map.html`)는 온라인 분기를 걷어낸 뒤에도 배경지도·궤적 정상
  (헤드리스 실측에서는 `--disable-gpu`를 붙이면 WebGL이 아예 안 잡혔고
  `--enable-unsafe-swiftshader` 단독이 동작했다 — BUILD.md 참고)

## 2026-09 검토 수정

- 분석 전에 원본 기준 해시와 전방 사본 SHA-256을 비교한다. 후방 사본도 별도로
  비교하며, 불일치·복사 실패·저장 실패 시 새 사건 레코드와 새 폴더를 정리한다.
- GPS 좌표·속도는 **현재 영상 시각 이하**의 정상 기록을 사용한다. 좌표 툴팁에서
  측정 시각/경과시간, GPS 시각 툴팁에서 UTC 원본을 확인할 수 있다.
- 속도 그래프·통계·위험운전 판정은 같은 유효 GPS 측정 기준을 쓴다. 체크섬/신뢰도 실패,
  이상치, 비유한 수치를 제외하고 반복 GPS 기록을 합친 산술평균이다(시간 가중 평균 아님).
  Location의 GPS 검증 열은 정상/실패/미제공을 구분한다. 미제공은 검증 성공이 아니다.
- 재생 실패 안내, 방향키 1초·±3초 버튼·프레임 이동, 주 영상 음량/음소거를 지원한다.
  음소거는 슬라이더를 0으로 내리고 실제 음량도 0으로 만든다(예전엔 `setMuted`만 불러 슬라이더가
  그대로였다). 해제하면 누르기 전 음량으로 돌아가고, 음소거 중 슬라이더를 올리면 해제, 0으로
  내리면 음소거가 된다.
  슬라이더 드래그는 놓을 때 탐색한다. 짧은 후방 영상은 범위 밖에서 멈추고 되감으면 복구된다.
- 분석 상태/경고 건수/슬랙 GPS 수를 표시한다(AVI 복구 여부는 AVI 사건에만 - MP4에 "AVI 복구 없음"이
  뜨는 건 혼란스럽다는 의견). 상태 줄 툴팁에서 경고 원문을 확인하고 보고서에도 경고를 남긴다.
  슬랙 좌표는 현재 영상 궤적과 합치지 않는다.
- 일반 MP4에서 지원 GPS 트랙이 없는 경우는 엔진 실패와 구분한다. `no_gps`는
  GPS를 추출하지 못했다는 뜻이며, 파일 안에 위치정보가 전혀 없다는 증명은 아니다.

지도 클릭→영상 탐색은 아직 제공하지 않는다. 기존 영상→지도 동기화는 유지한다.

### 증거·개인정보 취급

분석 사본, 원본 CSV, 로그, PDF에는 얼굴·차량번호·위치·담당자 정보가 포함될 수 있다.
사건 폴더와 보고서는 접근을 제한한 디스크에 보관하고 공개 저장소에 올리지 않는다.
온라인 카카오맵은 외부 지도 서버에 접속하며, 주소 조회 시 해당 좌표가 카카오 API로
전송된다. 외부 지도 링크도 브라우저로 좌표를 전달한다. 외부 전송이 허용되지 않은
자료는 오프라인 모드에서 분석하고 외부 지도 링크를 사용하지 않는다.
SHA-256 일치는 사본의 바이트 일치를 확인할 뿐 촬영 내용의 진실성이나 GPS 정확성을
보증하지 않는다. 원본은 별도로 보존하고 공유/제출본의 식별정보를 검토한다.

### 손상 AVI 복원 (별도 회수 도구)

Home의 **손상 AVI/MP4 복원**에서 형식을 AVI로 선택하고 손상 파일과 결과 저장 위치를 선택한다. 이 기능은 일반 Upload
분석·슬랙 카빙과 별개이며, 손상된 RIFF 시그니처 때문에 Upload가 거부하는 AVI도 받을 수 있다.
지원 대상은 **약 3.9 GiB 이하의 classic AVI, MJPEG 또는 Annex-B H.264 영상**이다.
AVI 모드는 OpenDML 여러 RIFF 전체 복원, 오디오 복원, 임의 코덱 복원을 지원하지 않는다.
MP4는 아래의 별도 MP4 모드를 사용한다.

- 영상 경계를 확인할 수 있으면 손상된 RIFF 헤더/크기 및 idx1 대신 새 AVI/idx1을 만든다.
  중간의 0 채움·불가능한 청크 크기를 만나도 뒤쪽 탐색을 계속한다.
- MJPEG는 청크 ID/크기까지 소실돼도 JPEG 본문과 해상도를 검증해 회수한다. 프레임을 어느
  스트림에 넣을지 유일하게 판단할 수 없으면 임의로 전방/후방을 지정하지 않는다.
- 스트림 헤더까지 소실됐으면 **동일 기기·코덱·해상도·FPS·채널 순서의 정상 AVI**를 참조로
  선택할 수 있다. 참조 영상에서는 설정만 사용하며 영상/GPS 내용을 복사하지 않는다.
  참조의 적합성을 모든 기기에 대해 자동 입증하지 못하므로 사용자가 확인해야 한다.
- 참조도 없으면 프레임 속도를 만들어내지 않고 가능한 JPEG 정지영상 후보와 GPS만 회수한다.
  H.264는 살아 있는 SPS/PPS와 IDR부터 시작한다. 참조 프레임/코덱 설정이 사라졌거나 영상 본문이
  손상되면 일부 또는 전부 재생되지 않을 수 있다. 삭제·덮어쓴 바이트를 복구하는 기능은 아니다.
- 파일 전체에서 체크섬·좌표·날짜/시각이 유효한 NMEA RMC를 찾아 `recovered_gps.csv`에
  원본 바이트 위치와 UTC를 남긴다. (0,0), 체크섬 실패, 무효 GPS는 제외한다. 독자 이진 GPS와
  G센서 복원은 이 기능의 지원 대상이 아니다. 전체 스캔에는 과거 녹화/슬랙이 섞일 수 있어
  **일반 분석 궤적과 합치지 않는다.**
- 영상은 살아 있는 movi 경계 또는 실제 청크 ID·크기·오프셋을 대조한 idx1 앞까지만 회수한다.
  헤더가 사라져도 idx1의 상대/절대 오프셋을 검증해 뒤쪽 슬랙을 제외한다. 뒤에 붙은 별도 AVI의
  경계를 첫 영상의 경계로 사용하지 않는다. 경계를 확인할 수 없으면 정상 참조가 있어도
  **AVI 생성을 보류**하고 GPS/JPEG 후보만 별도 회수한다. 이때 JPEG도 슬랙을 포함할 수 있으며
  `jpeg_scope=whole_file_untrusted`로 기록한다. 영상 경계 판정과 보류 사유는
  `video_boundary_verified`, `video_withheld_reason`, `video_scan_range`에서 확인한다.

결과는 새 `avi_recovery_*` 폴더에 저장한다. 원본을 수정하지 않고 `damaged_source.avi` 사본의
SHA-256을 대조한다. `recovery.json`은 원본·참조·복원 영상 해시, 탐색 범위, 회수 프레임 수,
디코딩 결과를 기록한다. `frame_offsets.csv`/`jpeg_offsets.csv`는 각 회수 항목의 원본 위치다.
취소·오류 시 임시 폴더를 정리하고, 이미 존재하는 결과 폴더는 덮어쓰지 않는다.

**복원 AVI는 손실 구간을 제거한 검토용 영상이다. 원래 시간축을 복구한 영상이 아니다.**
GPS 동기화·사고 발생 시각·급가감속 계산의 입력으로 사용하지 않는다. 영상 스트림은 각각 별도
파일로 저장하며, 손실된 음성이나 GPS 타임라인을 만들어 넣지 않는다. 기존 사건 DB에는 자동 등록하지 않는다.

FFmpeg가 PATH에 있으면 복원 AVI **전체를 디코딩**해 검사한다(영상당 최대 120초).
`decode_check.status=passed`만 오류 로그 없이 후보 프레임 수 전체가 디코딩된 상태다.
FFmpeg 종료 코드가 0이어도 오류 로그가 있으면 `failed`, 디코딩 수가 후보 수와 다르면
`incomplete`로 기록한다. 없거나 오류/제한시간 초과이면
후보 파일은 보존하되 성공으로 표시하지 않는다. FFmpeg는 검증용 선택 의존성이며 EXE에 포함하지 않는다.
JPEG 정지영상은 구조 검사만 수행하며 전체 디코딩 성공으로 표시하지 않는다.

CLI에서도 같은 기능을 사용한다(저장소 폴더에서 실행).

```bash
python -m core.avi_recovery damaged.avi recovery_output
python -m core.avi_recovery damaged.avi recovery_output --reference normal_same_device.avi
python -m pytest -q tests
```

### 손상 MP4/fMP4 복원 (별도 회수 도구)

Home의 **손상 AVI/MP4 복원**에서 **MP4 / fMP4**를 선택한다. 일반 Upload 분석과 분리된
검토용 회수 기능이다. 사건 DB에 자동 등록하거나 회수 GPS를 기존 궤적과 합치지 않는다.
원본은 수정하지 않고 새 `mp4_recovery_*` 폴더에 사본과 결과를 저장한다.

- 16 GiB 이하 MP4/MOV/M4V의 **H.264/AVC 또는 HEVC 영상**을 지원한다. 살아 있는
  `moov`의 `stsc/stsz/stco/co64/stts/ctts`를 검증해 현재 녹화의 샘플 위치를 사용한다.
  앞 4 KB 손상, ftyp/mdat 시그니처·크기 손상, 부분 절단, 중간 덮어쓰기를 처리한다.
- `moov` 전체가 소실됐으면 **같은 기기·해상도·코덱·FPS의 정상 MP4**를 참조로 선택한다.
  참조의 코덱 설정/FPS/fragment 기본 설정만 사용한다. 참조의 영상·음성·GPS·샘플 표·
  composition 표를 복사하지 않는다. 참조가 없어도 본문에 유효한 SPS/PPS가 살아 있으면
  가능한 H.264를 회수한다. 설정이나 실제 FPS를 확인할 수 없으면 MP4 생성을 보류한다.
- 샘플 표 없는 본문 카빙은 **4바이트 길이 접두사의 H.264**를 지원한다. 카메라 트랙을
  구별할 수 없거나 다른 해상도의 SPS가 나타나면 생성을 보류한다. HEVC는 원본의 샘플
  표 또는 살아 있는 fMP4 fragment 위치 정보가 필요하다. 임의 코덱·독자 암호화 형식·
  삭제된 데이터 전체 복원·음성 복원은 지원하지 않는다.
- `moof/traf/tfhd/trun/tfdt`를 검증해 분할 MP4의 샘플을 찾는다. 손상된 fragment 뒤의
  정상 `moof`를 다시 탐색하며, 초기화 헤더 소실 시 정상 참조를 사용할 수 있다.
- 긴 0 채움·잘못된 NAL 길이·손실된 예측 연결을 만나면 다음 독립 IDR부터 재개한다.
  처음 생성한 영상의 검증이 실패하면 독립 GOP별로 재검증해 실패한 GOP를 제외한다.
  실제 영상에서 쓰는 짧은 CABAC/정렬용 0 패딩은 중간 덮어쓰기와 구분한다.
- 영상은 재인코딩하지 않는다. 새 MP4의 `mdat/moov`와 크기·위치·키프레임·표시 순서
  표를 재구성한다. H.264 B프레임은 원본 ctts 또는 progressive POC type 0으로 표시
  순서를 재구성한다. 원래 시간축과 사건 시각을 보존했다는 의미는 아니다.
- `free/skip` 슬랙과 뒤에 붙은 다른 MP4의 영상은 결과에 합치지 않는다. 원본 샘플 표가
  없고 mdat 안에 다른 녹화 헤더가 발견되면 그 앞까지만 회수한다. 본문 경계 근거 자체가
  없으면 영상 생성을 보류한다. 참조 영상만으로 경계 근거를 만들어내지 않는다.
- GPS는 `$` 유무와 관계없이 체크섬·날짜/시각·좌표·fix가 유효한 NMEA RMC/GGA만 회수한다.
  (0,0), NaN/Inf, 체크섬 실패와 무효 fix는 제외한다. GGA의 없는 날짜는 만들지 않는다.
  지원하는 텍스트 `gsensori` 계열 G센서도 회수한다. 두 CSV 모두 파일 전체 별도 후보이며
  `whole_file_untrusted`로 기록한다. 슬랙/과거 녹화 후보가 포함될 수 있다.

`recovery.json`에 원본·참조·복원 영상 SHA-256, 사본 해시 대조, 탐색 경계, 회수량,
제외 사유와 전체 디코딩 결과를 기록한다. `frame_offsets.csv`는 프레임별 원본 위치이며,
`nal_offsets.csv`는 실제 복사한 영상 바이트 구간이다. 본문 카빙의 프레임 extent에는
음성/텍스트 틈이 포함될 수 있으므로 정확한 복사 범위는 NAL 표를 사용한다.
`recovered_gps.csv`/`recovered_gsensor.csv`에도 각각 원본 바이트 위치를 기록한다.
원본/참조가 복원 중 변경되면 결과를 폐기하며 취소·오류 시 임시 결과를 정리한다.
이미 존재하는 결과 폴더는 덮어쓰지 않는다.

MP4 생성은 표준 라이브러리로 수행한다. FFmpeg가 PATH에 있으면 **전체 영상 디코딩**을
수행해 오류 로그가 없고 실제 디코딩 수가 회수 프레임 수와 일치하는지 확인한다.
`decode_check.status=passed`만 검증된 결과다. FFmpeg가 없으면 `not_run`인 후보로 저장한다.
오류·불일치·시간 제한 초과 결과는 검증된 MP4로 제시하지 않는다.
재구성한 영상은 손실 구간이 압축된 **검토용**이며 GPS 동기화·사고 시각·급가감속
판정에 사용하지 않는다. 삭제·덮어쓴 바이트를 재생성하거나 임의의 MP4 복원을 보장하지 않는다.

```bash
python -m core.mp4_recovery damaged.mp4 recovery_output
python -m core.mp4_recovery damaged.mp4 recovery_output --reference same_device_normal.mp4
python -m core.mp4_recovery damaged.mp4 recovery_output --reference same_device_normal.mp4 --fps 30000/1001
python -m pytest -q tests
```
